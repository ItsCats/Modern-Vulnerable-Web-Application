How it works

A short loop that builds lasting intuition

Each lab follows the same three steps, so you spend your time on the vulnerability rather than on the tooling.

  1. 01

    Exploit

    Attack a working feature — a login form, a file download, a money transfer — until you complete each objective. Hints are available if you get stuck.

  2. 02

    Understand

    Read the server-side code that handled your request, with the vulnerable line highlighted, and the reason the payload worked.

  3. 03

    Fix

    Raise the security level and watch the same payload fail. Compare the weak and secure implementations side by side.

Three security levels in every lab

Switch levels at any time to see how a defense changes the outcome of the same attack.

Low Vulnerable

No defences. The code makes the classic mistake, so textbook payloads work and the root cause is easy to see.

Medium Weak mitigation

A plausible but flawed fix, such as a keyword blocklist or a Referer check. Learn why partial defences fail and how they are bypassed.

High Secure

The fix you would ship to production: parameterized queries, output encoding, CSRF tokens, authorization checks and safe APIs.

Under the hood

Realistic behavior, zero infrastructure

The back-ends are simulated in the browser, so the labs are safe to run anywhere and can be hosted as plain static files.

Entirely client-side

Static HTML, CSS and vanilla JavaScript with no build step. Every simulated request is handled inside the page, so lab data never reaches a server.

A real SQL engine

The SQL injection lab runs genuine SQLite compiled to WebAssembly (sql.js), so UNION queries and schema enumeration behave exactly as they would on a server.

Isolated in a Web Worker

The ReDoS lab evaluates regular expressions off the main thread with a hard timeout, so catastrophic backtracking stalls the simulated server, not your tab.

Mapped to industry standards

Each lab references its OWASP Top 10:2025 category and CWE identifier, linking the exercise to the vocabulary used in real assessments.

No install, no accounts

Open the site and start. There is nothing to configure. The only external resources are web fonts and the sql.js runtime, both loaded from public CDNs.

Accessible light and dark UI

Semantic markup, keyboard-friendly controls, visible focus states, reduced-motion support and a theme that follows your system preference.

About

Built for learning secure development

MVWA is aimed at developers, students and anyone preparing for application-security work. It is a modern, browser-only take on classic training targets such as DVWA: instead of running a deliberately insecure server, every lab ships with a small simulated back-end and the exact code that makes it vulnerable.

The goal is not to memorize payloads but to recognize the underlying pattern — untrusted input reaching an interpreter, a missing authorization check, an unbounded algorithm — and to know what the correct fix looks like.

Responsible use

This project is intentionally insecure and exists for educational purposes only. The techniques it teaches are illegal to use against systems you do not own. Never test a website, application or network without explicit written authorization from its owner.

Everything in MVWA runs locally in your browser, so practicing here harms no one.
