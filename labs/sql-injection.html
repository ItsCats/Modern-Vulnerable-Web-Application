Server-side implementation

routes/store.js

User input is concatenated directly into the SQL string, and raw database errors are returned to the client. The samples use better-sqlite3.

Low · vulnerableNode.js
app.get("/products", (req, res) => {
  const sql = "SELECT id, name, category, price FROM products " +
              "WHERE released = 1 AND name LIKE '%" [[bad]]+ req.query.q +[[/bad]] "%'";
  try {
    res.json(db.prepare(sql).all());
  } catch (err) {
    res.status(500).send([[bad]]err.message[[/bad]]);          // leaks database errors
  }
});

app.post("/staff/login", (req, res) => {
  const { username, password } = req.body;
  const sql = "SELECT id, username, role FROM users " +
              "WHERE username = '" [[bad]]+ username +[[/bad]] "' AND password = '" [[bad]]+ password +[[/bad]] "'";
  const user = db.prepare(sql).get();
  user ? startSession(res, user) : res.status(401).end();
});

A developer added a blocklist that strips "dangerous" keywords. The query is still built by concatenation.

Medium · weak mitigationNode.js
// Remove keywords commonly used in SQL injection payloads
function sanitize(input) {
  return input.replace([[bad]]/OR|UNION|SELECT|--/g[[/bad]], "");   // case-sensitive, single pass
}

app.get("/products", (req, res) => {
  const q = sanitize(req.query.q);
  const sql = "SELECT id, name, category, price FROM products " +
              "WHERE released = 1 AND name LIKE '%" [[bad]]+ q +[[/bad]] "%'";
  try {
    res.json(db.prepare(sql).all());
  } catch (err) {
    res.status(500).send(err.message);
  }
});

Parameterized queries keep code and data separate: the statement is compiled first, and user input is bound afterwards as a value that can never change the query's structure.

High · secureNode.js
const searchProducts = db.prepare(
  "SELECT id, name, category, price FROM products WHERE released = 1 AND name LIKE [[good]]?[[/good]]"
);
const findStaff = db.prepare(
  "SELECT id, username, role, password_hash FROM users WHERE username = [[good]]?[[/good]]"
);

app.get("/products", (req, res) => {
  res.json(searchProducts.all([[good]]`%${req.query.q}%`[[/good]]));
});

app.post("/staff/login", async (req, res) => {
  const user = findStaff.get([[good]]req.body.username[[/good]]);
  const ok = user && await argon2.verify(user.password_hash, req.body.password);
  if (!ok) return res.status(401).json({ error: "Invalid credentials" });   // generic error
  startSession(res, user);

How the attack works

Root cause

When an application builds a query by concatenating strings, the database cannot tell which characters came from the developer and which came from the user. A single quote in the input closes the string literal early, and everything after it is interpreted as SQL. The payload admin'-- turns the login query into WHERE username = 'admin'--' AND password = '…': the password check is commented out.

Impact

  • Authentication bypass and account takeover.
  • Disclosure of the entire database via UNION SELECT, including credentials and personal data.
  • Data modification or destruction through stacked queries such as ; DROP TABLE users, on drivers that allow several statements per call (mysql2 with multipleStatements, SQL Server, PostgreSQL's simple query protocol). better-sqlite3, used here, rejects them. Try it.
  • On some engines, file system access or command execution on the database host.

Why the Medium fix fails

Blocklists try to enumerate every bad input, and attackers only need one they missed. SQL keywords are case-insensitive, so union passes a case-sensitive filter; /* comments replace --; and single-pass removal can be defeated by nesting, as in UNIUNIONON.

Remediation

  • Use parameterized queries or prepared statements for every query, including those built by ORMs with raw fragments.
  • Allowlist identifiers that cannot be parameterized, such as sort columns and table names.
  • Run the application with a least-privilege database account, and keep multi-statement execution disabled in the driver.
  • Return generic error messages and log the details server-side.
  • Store passwords with a slow, salted hash (Argon2id, scrypt or bcrypt), never in plaintext.
