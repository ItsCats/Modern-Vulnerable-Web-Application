Target: Pulse sign-up API

Node.js · single event loop

Pulse validates email addresses with a regular expression before creating an account. Node.js runs JavaScript on a single thread, so while one regex is running, every other request waits. Here the server's regex runs in a Web Worker, which keeps your tab responsive and kills any request that takes longer than 4 seconds.

Server-side implementation

routes/signup.js

The local part ([a-zA-Z0-9_.-]+)+ nests one quantifier inside another. When the match fails, the engine tries every way of splitting the input between the inner and outer loops: 2n combinations.

Low · vulnerableNode.js
const EMAIL_RE = /^[[bad]]([a-zA-Z0-9_.-]+)+[[/bad]]@([a-zA-Z0-9-]+\.)+[a-zA-Z]{2,}$/;

app.post("/signup", (req, res) => {
  if (![[bad]]EMAIL_RE.test(req.body.email)[[/bad]]) {         // blocks the event loop
    return res.status(400).json({ error: "Invalid email" });
  }
  createAccount(req.body);
  res.status(201).end();
});

A maximum length was added to stop the attack. Because the cost doubles with every character, 32 characters are still enough to stall the server for seconds.

Medium · weak mitigationNode.js
const EMAIL_RE = /^([a-zA-Z0-9_.-]+)+@([a-zA-Z0-9-]+\.)+[a-zA-Z]{2,}$/;

app.post("/signup", (req, res) => {
  const email = String(req.body.email);
  if ([[bad]]email.length > 32[[/bad]]) return res.status(400).json({ error: "Email too long" });
  if (!EMAIL_RE.test(email)) return res.status(400).json({ error: "Invalid email" });
  createAccount(req.body);
  res.status(201).end();
});

The pattern has no nested or overlapping quantifiers, so it runs in linear time. A sensible length cap (RFC 5321 allows 254 characters) bounds the work anyway. For untrusted patterns, use a linear-time engine such as RE2.

High · secureNode.js
const EMAIL_RE = /^[[good]][a-zA-Z0-9_.-]+[[/good]]@(?:[a-zA-Z0-9-]+\.)+[a-zA-Z]{2,}$/;   // no nested quantifiers

app.post("/signup", (req, res) => {
  const email = String(req.body.email);
  if ([[good]]email.length > 254[[/good]] || !EMAIL_RE.test(email)) {
    return res.status(400).json({ error: "Invalid email" });
  }
  createAccount(req.body);
  res.status(201).end();
});

How the attack works

Root cause

JavaScript, Python, Java and .NET use backtracking regex engines. If a pattern can match the same text in many different ways, as with nested quantifiers like (a+)+ or overlapping alternatives like (a|a)*, a nearly-matching input that ultimately fails makes the engine explore every possibility. The work grows exponentially with input length.

Impact

  • One small request can pin a CPU core for seconds or minutes.
  • On single-threaded runtimes such as Node.js, every other user's request stalls until it finishes.
  • Real incidents include Cloudflare's 2019 global outage and Stack Overflow's 2016 outage.

Why the Medium fix fails

Length limits treat the symptom. Because each extra character doubles the work, the limit would have to be very short to be safe, short enough to reject legitimate input. The vulnerable pattern is still there, and a faster attacker loop or a slightly longer limit brings the outage back.

Remediation

  • Rewrite patterns to avoid nested and overlapping quantifiers, and use possessive quantifiers or atomic groups where the engine supports them.
  • Use a linear-time engine (RE2, Rust regex, or the re2 package in Node) for complex or user-supplied patterns.
  • Cap input length before matching, and set execution time limits where the platform supports them (.NET matchTimeout).
  • Lint for vulnerable patterns in CI with tools such as eslint-plugin-regexp or safe-regex.
