How the attack works

Root cause

Browsers attach a site's cookies to requests sent to that site, whichever page started the request. If a server identifies the user by cookie alone, it cannot tell a request the user meant to send from one forged by another site. The attacker never sees the response. They don't need to, because the state change (a transfer, an email change, a password reset) is the goal.

Impact

  • Unauthorized fund transfers, purchases or account setting changes.
  • Account takeover by changing the account's email address or password.
  • Admin actions performed through a privileged user's browser.

Why the Medium fix fails

Substring checks match attacker-controlled hosts such as bank.harbor.test.attacker.test. Allowing a missing Referer is also exploitable, because the attacker's page can suppress it with <meta name="referrer" content="no-referrer">. Requiring POST alone does nothing: a hidden form can POST just as easily.

Remediation

  • Use a synchronizer token or a signed double-submit cookie on every state-changing request. Most frameworks ship this built in.
  • Set session cookies to SameSite=Lax or Strict as defense in depth.
  • Verify the Origin header (or Sec-Fetch-Site) against an exact allowlist.
  • Never change state on GET. Ask for re-authentication before sensitive actions.
