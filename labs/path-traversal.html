Target: Contoso Docs

BASE_DIR = /var/www/docs/files

Contoso's document portal serves files with GET /download?file=<name>. The server joins the name onto its files directory and streams back whatever it finds. Edit the file parameter just as you would in a browser address bar. It is URL-decoded once, as a web framework would do it.

Server-side implementation

routes/download.js

path.join resolves .. segments, so a name like ../../../etc/passwd walks out of the base directory. Error messages leak absolute paths, which tells the attacker how deep the base directory is.

Low · vulnerableNode.js
const BASE_DIR = "/var/www/docs/files";

app.get("/download", (req, res) => {
  const target = [[bad]]path.join(BASE_DIR, req.query.file)[[/bad]];
  fs.readFile(target, (err, data) => {
    if (err) return res.status(err.code === "ENOENT" ? 404 : 500).send([[bad]]err.message[[/bad]]);
    res.type("text/plain").send(data);
  });
});

The developer strips ../ from the input and, to handle file names that were encoded twice, decodes them again afterwards. Both steps are mistakes.

Medium · weak mitigationNode.js
app.get("/download", (req, res) => {
  // Remove directory traversal sequences
  const cleaned = req.query.file[[bad]].replaceAll("../", "")[[/bad]];        // non-recursive
  const name = [[bad]]decodeURIComponent(cleaned)[[/bad]];                     // decoded AFTER filtering
  const target = path.join(BASE_DIR, name);
  fs.readFile(target, (err, data) => {
    if (err) return res.status(404).send(err.message);
    res.type("text/plain").send(data);
  });
});

The input is canonicalised once with path.resolve, and the result must stay inside the base directory. Better still, files are looked up by ID in a database so user input never reaches the file system.

High · secureNode.js
const BASE_DIR = path.resolve("/var/www/docs/files");

app.get("/download", async (req, res) => {
  const name = String(req.query.file ?? "");
  if (name.includes("\0")) return res.sendStatus(400);
  const target = [[good]]path.resolve(BASE_DIR, name)[[/good]];
  if ([[good]]!target.startsWith(BASE_DIR + path.sep)[[/good]]) return res.sendStatus(404);
  const real = await fs.promises.realpath(target).catch(() => null);  // defeat symlinks
  if (!real || [[good]]!real.startsWith(BASE_DIR + path.sep)[[/good]]) return res.sendStatus(404);
  res.type("text/plain").sendFile(real);
});

How the attack works

Root cause

When a file path is built from user input, the special segment .. ("parent directory") lets the input climb out of the intended folder. The application's own permissions then decide what can be read, and a web server can usually read its source code, configuration and many system files.

Impact

  • Disclosure of credentials in .env files, cloud keys and database connection strings.
  • Source code disclosure, which makes every other bug easier to find.
  • Account and host enumeration through files like /etc/passwd.
  • Remote code execution where traversal applies to uploads or writes (Zip Slip, log poisoning).

Why the Medium fix fails

Stripping ../ in a single pass turns ....// back into ../. Decoding after validating means %2e%2e%2f passes the filter and becomes ../ afterwards. Validate the final, canonical path, never the raw input.

Remediation

  • Avoid passing user input to file system APIs at all: map an ID or an allowlisted name to a path.
  • Otherwise decode once, canonicalise (path.resolve plus realpath) and check the result is inside the base directory.
  • Run the service as a low-privilege user, and keep secrets out of the web root. A secrets manager is better than a .env file.
  • Return generic errors that don't reveal absolute paths.
