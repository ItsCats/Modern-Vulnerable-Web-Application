Server-side implementation

routes/api.js

The handlers check that the caller is authenticated, but never that they are authorised for the object they asked for. Whole database records are serialised into the response.

Sequential IDs were judged "too guessable", so the API now uses encoded references. The encoding is plain base64 and there is still no ownership check.

Every lookup is scoped to the authenticated user. Objects you don't own return 404, so the API doesn't even reveal which IDs exist. Responses go through an explicit DTO that never includes secrets.

How the attack works

Root cause

An IDOR exists when an application uses an identifier supplied by the client to fetch an object, and doesn't check that the current user is allowed to access that object. Authentication answers who are you?, while authorization answers may you touch this?. IDOR is a missing authorization check. It is the most common way Broken Access Control, number one in the OWASP Top 10, shows up in APIs, where it is also called BOLA (API1:2023).

Impact

  • Horizontal privilege escalation: reading or changing other users' data.
  • Vertical privilege escalation: reaching admin-only records or credentials.
  • Mass data exposure, because sequential IDs make it trivial to enumerate every record.

Why the Medium fix fails

Encoding is not access control. Base64, hex and hashes of predictable values can all be reversed or recomputed in seconds. Even random UUIDs only make guessing harder: they leak through URLs, logs and shared links, and they leave the actual authorization flaw in place.

Remediation

  • Enforce object-level authorization on every request, server-side, ideally in a central policy layer rather than ad hoc in each handler.
  • Scope database queries to the current user or tenant (WHERE owner_id = ?).
  • Return explicit DTOs and never serialise whole records, so secrets are never sent by accident.
  • Write automated tests that request other users' objects with each role and expect a denial.
