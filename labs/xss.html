Server-side implementation

routes/shop.js

User-controlled data is inserted into HTML without encoding, so the browser parses it as markup and runs any script it contains. The session cookie is readable from JavaScript.

How the attack works

Root cause

XSS happens when untrusted data is written into a page in a context where the browser interprets it as code. Reflected XSS bounces a payload off a request, usually a link the victim clicks. Stored XSS saves the payload on the server, so it runs for every user who views the page. Either way the script runs with the site's origin and can do anything the user can.

Impact

  • Session hijacking by reading document.cookie or tokens in storage.
  • Performing actions as the victim, which defeats CSRF tokens.
  • Credential phishing through injected login forms, keylogging and page defacement.
  • Self-propagating worms on social platforms, through stored XSS.

Why the Medium fix fails

Script tags are only one of dozens of execution vectors. Event-handler attributes (onerror, ontoggle, onfocus), javascript: URLs and SVG elements all run code without a <script> tag. Sanitizing HTML correctly requires a real parser such as DOMPurify. A regular expression is not enough.

Remediation

  • Encode output for its context (HTML body, attribute, URL, JavaScript). Prefer templating engines that auto-escape, and avoid innerHTML in favor of textContent.
  • If rich HTML is required, sanitize it with a maintained library (DOMPurify) and an allowlist.
  • Deploy a strict Content Security Policy (nonces or hashes, no 'unsafe-inline').
  • Mark session cookies HttpOnly, Secure and SameSite.
  • Use Trusted Types to lock down DOM sinks in large front-end codebases.
